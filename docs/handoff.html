THE SEQUENCE

Three in order, one in parallel

H1 to H3 each depend on the one before. H4 touches no Worker code, so it can start any day.

H1

One Worker, one origin

H1

One Worker serves the SPA and runs the API

APP_UI_ORIGIN stops existing, because it is the same as APP_ORIGIN.
Why here

Two origins are two websites as far as a browser is concerned. H2 adds a cookie, and a cookie that has to cross origins is the classic bug that only appears in production. Remove the second origin before you add the cookie, not after.

The work
  1. Wrangler 3 to 4. Version 4.20 or higher is required by the next step.
  2. Add the assets block and run_worker_first.
  3. Point APP_ORIGIN at the address the Worker answers on.
  4. Delete APP_UI_ORIGIN and the branch in routes/auth.ts that chooses between the two.
"assets": {
  "directory": "../app/dist",
  "not_found_handling": "single-page-application",
  "binding": "ASSETS",
  "run_worker_first": ["/api/*", "/auth/*"]
}
The trap

Without run_worker_first, Cloudflare routes on the Sec-Fetch-Mode header. The OAuth callback is a browser navigation, not an XHR, so it gets index.html and never reaches the Worker. Sign-in then fails with nothing in the Worker log, because the Worker never ran.

You decide

Where wrangler.jsonc lives afterwards. It points at ../app/dist and at worker/src, so the repository root is the natural home, and ADR-0002 expects it there.

Done when

bun run build, then bunx wrangler dev serves the SPA and answers /api/health from one port. Sign-in still works.

H2

better-auth, on D1

H2

better-auth owns the session, D1 owns the tokens

Sign-in behaves exactly as it does today. That is the test of success.
Why here

Every D1 table needs a user row as a foreign key, and a stateless cookie cannot be one. That reason alone is sufficient.

The real prize is different: you cannot cancel a sealed cookie. Today a session stays valid until it expires and nothing can stop it. After this change, “sign out everywhere” works and “remove this person from the studio” works. Keep that in front of you — it tells you when the work is correct.

The work
  1. Bind D1. Create better-auth's tables and a studio table.
  2. Do not touch the OAuth flow. routes/auth.ts is 334 lines of correct Frappe code. SEAM section 2 gives three reasons not to move it into a better-auth plugin.
  3. Change one step only: at the end of /auth/callback, find or create the better-auth user, then create a session. better-auth owns the cookie from then on.
  4. Write the ERPNext access and refresh tokens to the account table, keyed by user and studio. Never a token in a cookie.
  5. Delete the exclude list from worker/tsconfig.json. D1 exists again, so those files get type-checked again.
You decide

The shape of the studio table and how it joins better-auth's organization table. host is the key. Read SEAM section 8 first: KV holds the client credentials because requireSession reads them before the user is known, and D1 holds the rest.

Stop and ask

If you find yourself writing a permission check inside StudioOS, stop. This backend has no permission code and that is the design, not an omission.

Done when

Someone signs in with ERPNext and sees exactly what they saw before. Then you delete their session row in D1 and their next request fails. The second test is the one that matters.

H3

Sign in with Google

This is the piece with a real design problem inside it. Solve the problem on paper before you build the button.

H3

The security question inside it

One person, two sign-in methods. One account or two?
The rule

If you join two accounts, join them only on an email address the provider states it has verified. Google verifies addresses. Joining on an unverified address means someone registers with another person's email and inherits that person's studio access. This attack has a name — account linking by unverified email — and no code review catches it.

Write your answer in an ADR before you write the code.

You decide

How the two buttons sit together on the page, and what a person sees after Google sign-in and before a studio is connected.

Stop and ask

Ask Malhar before you join two accounts by any rule other than a verified email address.

Done when

A new person signs in with Google, gets a clear next step, and connects their ERPNext. Then the same person signs in with ERPNext directly and lands on the same account, not a second one.

H4

Front end conventions, and Figma

H4 · PARALLEL

Shubham hands you a Figma file. It becomes code without a negotiation each time.

This is your area. The recommendation below is a starting point, not an instruction.
What exists

React 19, Vite, TypeScript, Tailwind v4, React Router 7, TanStack Query, React Hook Form with Zod, Chart.js, date-fns. Features are already sliced by folder in app/src/features/. The gap is not the libraries. The gap is that none of it is written down, so every new page is a fresh set of small decisions.

Recommended

shadcn/ui for components. The code is copied into the repo rather than installed, so you own it and can change it. It is Tailwind-native, and an agent knows it well — which matters more here than it usually would.

Figma variables become Tailwind theme tokens. Tailwind v4 declares a theme in CSS with @theme. A colour or spacing value from Figma becomes one token in one file, and components name the token rather than the value. Shubham changes a colour, you change one line.

Write it down in app/AGENTS.md. Folder structure, token names, which component for which job, and what a feature folder may import. That file is the front end's half of the rules.

Stop and ask

Before adding a library with its own design opinion — Material UI, Chakra, Mantine. Making those agree with a Figma file costs more than they save.

Done when

You build one screen from Figma, write down what you did as the convention, then build a second screen and the convention does not change.

ALWAYS

The three questions

Ask these of every new field, table, endpoint and migration. Question 1 answers most decisions on its own. Questions 2 and 3 exist because their failures produce no error message.

QUESTION 1

Does this survive deleting StudioOS?

Yes: it goes in ERPNext. No: it goes in D1.

QUESTION 2 · SILENT

Does reading it reveal an ERPNext document?

Yes: wrap the read in withDocAccess, and let ERPNext's 403 be your 403.

QUESTION 3 · SILENT

Does it need a credential with no user?

Yes: stop. The design is wrong. No service account, no API key, no token “just for the cron”.

METHOD

Working with the agent

The agent writes faster than you. Your job is the part it cannot do: deciding whether the thing being built should exist in that shape.

  • Ask it which question it touched. Before accepting a diff: “which of the three questions does this touch, and what did you decide?” If it cannot answer, the change is not ready.
  • Give it the file, not the answer. “Read SEAM section 5, then write the endpoint” beats “add a permission check” — the second one teaches it the wrong lesson about this codebase.
  • When you disagree with a document, the document is sometimes wrong. That has happened here already. Change the document first, in writing, with a reason. Never route around it in code.
  • Write down what you decided not to do. Nobody can reconstruct that later, and in three months you are nobody.
  • Working code you cannot explain is a liability with a delay fuse. If the agent produces something that passes and you cannot say why, that is the moment to slow down, not to merge.
