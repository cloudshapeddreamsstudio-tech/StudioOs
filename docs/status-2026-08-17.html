Where the project stands

StudioOS is a purpose-built interface for film production studios that run their business on ERPNext. ERPNext holds the data; StudioOS makes it usable. Phase 1 is complete and running against real data. The project has since changed shape — from an internal tool for one studio into a product sold to many — and this brief covers what that change forced us to verify.

What the scope change forced

The original plan authenticated one person at the network edge, and reached ERPNext with a single administrator key. That is sound for one user and unusable for a product: one shared key means every employee at every studio would see everything, including payroll, and one leaked secret would expose every customer at once.

So the question became: can a studio owner sign in to StudioOS using the ERPNext account they already have? If yes, we never handle a password, and ERPNext enforces its own permissions on our behalf.

The finding

Yes — and it is tested, not assumed. Each studio's ERPNext can register StudioOS as a known application and then act as the identity provider for that studio's staff.

What we needed to knowWhat we foundEvidence
Does managed ERPNext hosting allow outside apps to register? Yes. Another vendor's application is already registered on our own production site. Live site inspection
Does ERPNext expose the sign-in machinery we need? Yes, and it publishes a directory of its own endpoints, so we hardcode nothing per customer. HTTP 200, all endpoints present
Do the endpoints actually work? Yes. The login endpoint redirects correctly and the token endpoint returns valid, standards-compliant responses. Live request/response
Can registration be automated, so customers do not do it by hand? Yes. Our connector app creates it on install, updates it safely, and removes it on uninstall. Full cycle tested on dev bench

Why this matters commercially. Because the studio's own ERPNext decides who may see what, we do not build, test, or take responsibility for a permissions system. A studio's editor sees schedules; only the owner sees the money. That behaviour is inherited, not written.

How signing in works

The one thing to understand: the person's password goes to their own ERPNext, never to us. We receive only a temporary token that says who they are and what they may see.

What the studio owner actually sees

Two screens carry the whole thing. Note that signing in is a field and a button, not a button alone — with every studio on its own ERPNext, StudioOS has to be told which one before it can send anyone anywhere.

Both screens are proposed designs, not photographs of shipped software. The behaviour they describe is verified; the visual treatment is not final.

What this changes about security

This is the single largest improvement in the release. It replaces one all-powerful key with a token per person.

The stack decision

Because ERPNext is built on the Frappe framework, the fair question is whether StudioOS should be built on Frappe too. We evaluated it seriously — Frappe's own products are built exactly that way. The diagram below is the difference the choice actually turns on.

Weighing the two honestly

  Built on Frappe React + Hono (chosen)
Shipping updates − Each customer must update their own server + We deploy once; every studio gets it immediately
Interface quality − Bounded by Frappe's own UI conventions + Complete control — which is the entire reason StudioOS exists
Work already done − Phase 1 discarded and rewritten in a different language + Phase 1 kept, already verified against live data
Permissions + Inherited automatically from ERPNext + Also inherited, once sign-in ships — this was the open risk, now closed
Speed of data access + Reads the database directly, no network hop − Every read crosses the internet; needs caching
Hosting & running cost + Runs on the customer's existing server; nothing for us to run − We run and pay for the platform (small, but ours)
Credential handling + Nothing to store; it never leaves the customer's site − We hold each studio's tokens — needs encryption and a breach plan
ERPNext version changes + Breakage surfaces at install time − Can break silently at runtime; needs monitoring
Team fit − Python and Vue; two toolchains to maintain + One language across front and back end

The decision. Frappe wins on data access speed and on having nothing to host. React and Hono win on the two things that decide whether this is a product: we can ship to every customer at once, and we control the interface completely. The permissions advantage that once favoured Frappe is now matched, because sign-in with ERPNext gives us the same inheritance. We are staying on React + Hono, and StudioOS is not being rebuilt on Frappe.

The connector app

One small companion app does still get installed on each customer's ERPNext. It ships no interface. Its job is to register StudioOS on their site automatically, so the studio owner never has to configure anything by hand — and, critically, to remove that registration cleanly if they ever uninstall us.

A real defect this caught. Removing the app did not remove its access credential — it stayed live on the site. A studio that dropped StudioOS would have kept a working key to its own books indefinitely. The connector now deletes the credential and every issued token on uninstall.

Built and tested end to end on the development server. Every path was exercised, including deliberately creating an access token first so the cleanup had something real to remove:
