The Seam

ERPNext holds the data that stays if you delete StudioOS. D1 holds the data that goes. Every rule on this page exists to keep that line, and the security property behind it, intact while other people — and other agents — write the code.

RULE 00

The application has no permission code

Each read and each write of studio data uses the access token of the person who signed in. StudioOS does not hold a credential that can read the accounts of a studio.

the security property · section 0

The backend is roughly 7000 lines. No line decides whether a user can see a document. ERPNext decides that before the data reaches StudioOS. The rule is not only a preference — it deletes a whole category of code.

What the rule gives

  • A safe failure mode — forgetting a check under-serves data, never leaks it.
  • One place to debug “I cannot see project X”: what does ERPNext permit? No second model, no cache, no sync.
  • Full control of StudioOS still yields an attacker no studio data. There is no credential to steal.

What the rule costs — read before you agree

  • A scheduled task has no user, so no token, so it cannot read ERPNext. Section 7 is this cost, not a separate decision.
  • Anything that runs while the user is away is hard: night reports, payment reminders.
  • An invited person with no ERPNext account gets the interface and no data. That is correct, not a bug.

One sentence starts the failure: “we need a service account for this task.” If a change needs StudioOS to read studio data with no user present, the design is wrong. Change the design — a code review cannot catch this.

how the rule breaks

An error in Section 1 makes an application that is hard to maintain. An error in Section 0 makes a data leak. That is why this is Section 0. Phase 6c removed the admin key to get this property; the history is the origin of the rule, not its reason.

RULE 02

Identity and authority are different questions

The questionAnswered byStored in
IdentityWho is this person? Do they have a StudioOS account? Which studio are they a member of?better-authD1
AuthorityCan this person see PROJ-0042?ERPNextNowhere. Asked again on every request.

A better-auth session does not grant access to data. It grants access to the interface. ERPNext decides what appears inside that interface, using that person's token.

Do not move the ERPNext sign-in into a better-auth plugin

  • genericOAuth providers are configured once, at start. StudioOS has a different issuer and different client credentials per studio. Per-request providers are not supported.
  • The sso plugin does register per-organization providers — and then verifies the ID token, issuer and sub. Frappe signs ID tokens with HS256. auth.ts deliberately skips the openid scope and asks the site itself via frappe.auth.get_logged_user, which answers about the token StudioOS actually holds.
  • routes/auth.ts is 334 lines of Frappe-correct code: the 301 discovery redirect on a bench versus the 200 on Frappe Cloud, the plain-HTTP host list, PKCE, state. Rewriting it inside a plugin will reintroduce those bugs.

Why better-auth at all

  • A user row. Every D1 table needs it as a foreign key. A stateless cookie cannot be one. This reason alone is enough.
  • organization, member, invitation — the multi-studio model. That is Phase 8.
  • Email sign-in, OTP, magic link. The ERPNext OAuth flow cannot start a studio before the connector is installed, and cannot invite someone with no ERPNext account.

Bind it with database: env.DB. D1 has no interactive transactions; better-auth uses batch() to stay consistent.

RULE 03

How a D1 row points at an ERPNext document

Three columns. Always all three. Every index on them starts with studio_id.

studio_id     TEXT NOT NULL REFERENCES studio(id),  -- which ERPNext site
erp_doctype   TEXT NOT NULL,                        -- 'Project'
erp_name      TEXT NOT NULL,                        -- 'PROJ-0042'
CREATE TABLE project_note (
  id          TEXT PRIMARY KEY,
  studio_id   TEXT NOT NULL REFERENCES studio(id),
  erp_doctype TEXT NOT NULL,
  erp_name    TEXT NOT NULL,
  author_id   TEXT NOT NULL REFERENCES user(id),
  body        TEXT NOT NULL,
  created_at  INTEGER NOT NULL
);
CREATE INDEX idx_project_note_doc
  ON project_note (studio_id, erp_doctype, erp_name, created_at DESC);

Do not copy ERPNext values into D1

Not project_name, not customer, not status, not grand_total — not even to render a list page fast. Two sources means one of them is wrong, and the client is the one who tells you. Keep the reference; read the values. Rule 04 is the only exception.

The reference points one way

D1 refers to ERPNext. ERPNext never refers to D1. No custom fields on ERPNext doctypes in v1. A custom_studioos_id on Project means you now maintain a Frappe app: migrations, version skew, an install step on every customer site. ERPNext must not know StudioOS exists.

Known v1 limitation: renaming a Frappe document orphans the D1 row. Accept it, record it, do not fix it now. A later version reconciles names with a webhook.

RULE 04

A cache is named like a cache

Sometimes you must copy ERPNext data into D1 — a dashboard that would otherwise make 40 requests, a scheduled job that needs yesterday's numbers. Allowed, on three conditions.

  1. The table name starts with cache_.
  2. It has a fetched_at column, and a written procedure to rebuild it.
  3. It is never the source of truth in a join, and never written back to ERPNext.

If the cache and ERPNext disagree, ERPNext is right and the cache is stale. If a procedure writes into a cache_ table, it is not a cache — rename it or delete it.

RULE 05

Permissions at the seam

Every read of D1 data that refers to an ERPNext document must first read that document from ERPNext, with the signed-in person's token, in the same request.

the control that fails silently · section 5

D1 rows carry no ERPNext permissions. Without this, a person who cannot open PROJ-0042 in ERPNext can still read the StudioOS notes attached to it. Order matters: ERPNext first, then D1. Never in parallel.

/**
 * Control access to StudioOS data with the permissions of ERPNext.
 *
 * The getDoc call is the permission check. ERPNext sends a 403 or 404 response
 * for a document that this user cannot see. That is also the correct response
 * for the StudioOS data about the document. StudioOS thus keeps no permission
 * logic of its own -- it only waits for the answer from ERPNext.
 */
async function withDocAccess<T>(
  c: Context<AppEnv>,
  doctype: string,
  name: string,
  fn: (studioId: string) => Promise<T>,
): Promise<T> {
  await c.get('frappe').getDoc(doctype, name);
  return fn(c.get('studioId'));
}
RULE 06

Two senders, one line between them

StudioOS sends email about StudioOS. ERPNext sends email about money.

section 6

Resend — from the StudioOS domain

  • sign-in links and OTP codes
  • studio invitations
  • connector-stopped alerts
  • product messages

ERPNext — from the studio

  • invoices and receipts
  • payment reminders
  • statements
  • everything the client's accounts team receives

No invoices from StudioOS in v1. Two senders for one invoice means two audit trails and a split domain reputation — and the client's accounts department gets money email from a domain they have never heard of. When StudioOS must send an invoice, it triggers ERPNext's own send.

Log every Resend call in D1: message id, template, recipient, status. The Resend dashboard cannot slice this per studio, and in week one somebody will ask whether an invitation actually went out.

RULE 07

No ERPNext when no user is present

This is Rule 00 restated for cron. No user, so no token, so no permissions.

RULE 08

One Worker, one origin

Two origins produce cookie and CORS failures that only appear in production. Serve the SPA and the API from the same Worker.

main = "src/index.ts"

[assets]
directory = "../frontend/dist"
not_found_handling = "single-page-application"
binding = "ASSETS"
run_worker_first = ["/api/*", "/auth/*"]

APP_ORIGIN cannot change later. The OAuth redirect URI is derived from it and registered on every customer's ERPNext site — change it and every customer reinstalls the connector.

the highest-cost mistake on this page

Pick the production hostname before the first customer registers. The first deploy is not the deadline. The first customer is.

The tenant registry splits by reader, not by convenience

SEQUENCE

The order is a gate, not a preference

Do not start a step before the previous one is finished.

  1. Agree to this document.If you disagree, change the document. Do not write different code.
  2. One Worker, one origin.Static assets plus run_worker_first. Set APP_ORIGIN to the production hostname. Wrangler 3 → 4.
  3. D1 and better-auth.better-auth tables plus studio. Wire the existing oauth4webapi callback to a better-auth session. Move ERPNext tokens into account. Success is measured one way: sign-in behaves exactly as before.
  4. Prove the seam with one feature.Project notes — the three columns from Rule 03 and withDocAccess from Rule 05. One feature that establishes two patterns beats five features with five patterns.
  5. Resend, for invitations and OTP only.Plus the email log.
  6. Deploy, and rewrite DEPLOY.md.It still documents the API key that Phase 6c removed.

The six Phase 10f data sets come after all of this, using Rule 01. They are the result of the seam, not part of building it.
