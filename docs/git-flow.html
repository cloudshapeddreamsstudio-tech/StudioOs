Git Flow

Demo runs the release branch. Production runs a tag on main. So the code that a person tests is the code that ships.

THE FLOW

One release

DEPLOY

Which code runs where

Demo
release/vX.Y.Z
demoos.cloudshapeddreamsstudio.com
Production
a tag on main
studioos.cloudshapeddreamsstudio.com

There is no dev branch. Only one release is in the demo test at one time.

STEPS

Five steps

1
Open the release branch from main. Write its scope.
2
One card, one branch. Cut it from main.
3
Merge the branch into the release.
4
Deploy the release to demo. A person tests it.
5
Malhar approves. Merge, tag, deploy production.
VERSION

One step at a time

Patch
a fault correction
v1.0.0 → v1.0.1
Minor
a new feature
v1.0.1 → v1.1.0
Major
a studio must act
v1.4.2 → v2.0.0

A small release is easy to test and easy to roll back.

ROLL BACK

Deploy the previous tag again

  • Do not merge an old release branch into main. It is already in main, so Git changes nothing.
  • A rollback changes the code. It does not change the database.
DATABASE

A migration only adds

After a rollback, the previous code runs on the new database. If the migration only added, that code still operates.

PARALLEL

Files that two branches change

worker/src/index.tsapp/src/router.tsxSidebar.tsxAGENTS.mddocs/tasks/README.mdbun.lockthe next migration number

The branch that merges second corrects the conflict.

RULES

For each person and each agent

  • Find your branch name before you change a file.
  • Start a feat/ or fix/ branch from main.
  • Run bun run check before you merge.
  • Do not commit to main.
  • Do not deploy demo from a feat/ or fix/ branch.
  • An agent does not merge, tag, or deploy production. A person does that.
docs/WORKFLOW.md is the rule. This page is the picture.
