1. What StudioOS is

StudioOS is a custom front-end for an ERPNext installation. The studio runs its real accounting in ERPNext (hosted on Frappe Cloud) — customers, projects, invoices, suppliers, payments. ERPNext's own UI is generic and built for every kind of business; StudioOS is a purpose-built layer on top of it that speaks the language of a film production studio: projects, shoots, crew, rental gear, invoices.

Crucially, StudioOS does not replace ERPNext and does not own its data. It reads and writes through ERPNext's REST API. If StudioOS disappeared tomorrow, every invoice and payment would still be in ERPNext, intact.

The one exception Some things the studio tracks have no home in ERPNext — studio rental sessions, ad-hoc transactions, per-project crew rosters, out-of-pocket expenses, subscriptions, invoice branding. StudioOS owns those in its own small database. That distinction runs through this whole document.

2. Why it was rebuilt

StudioOS replaces an earlier working app (the "CSDSxERPnext App"). That app was ~90 standalone HTML files with an Express server. It worked, but it had four structural problems:

Problem in the old appConsequenceHow StudioOS fixes it
Data stored in flat JSON files, written with fs.writeFileSync A crash mid-write truncates the file — losing the whole ledger, not one row A real database (D1). One row changes, one row is written.
Those JSON files were committed to git Any deploy that checks out the repo overwrites live data with stale copies Data lives in D1, outside the repo entirely
No authentication of any kind Anyone reaching the server had full read/write on the live accounting system Cloudflare Access authenticates at the edge, before any code runs
The sidebar was copy-pasted into all ~90 pages A nav change meant editing 90 files; pages silently drifted apart One <Sidebar> component, used everywhere
The old app is still running It remains the system the studio actually uses. StudioOS does not switch it off until feature parity is confirmed and verified side by side (Phase 6). Both apps must never write to the same ledgers at the same time — nothing reconciles them.

5. Who owns which data

This is the single most important thing to understand about StudioOS. Getting it wrong leads to data being stored twice and drifting apart.

ERPNext owns (read/write via REST)

  • Customers & Suppliers
  • Projects and their Tasks
  • Sales Invoices & Purchase Invoices
  • Payment Entries (the general ledger)
  • Items — the gear and service catalogue
  • Comments & Communications (the timeline)
  • File attachments

D1 owns (things ERPNext has no concept of)

  • rental_bookings + rental_sessions — studio hire
  • transactions — ad-hoc income/expense ledger
  • crew_entries — per-project crew & vendor roster
  • expenses — out-of-pocket spend
  • subscriptions — recurring costs
  • brand — invoice branding & bank details
Why the backup matters so much Those D1 tables are the only copy of that data anywhere. ERPNext does not have it. In the old app they were flat JSON files on one laptop, in a git repo with no remote. StudioOS dumps all seven tables to R2 storage every night, as plain readable JSON rather than a SQL dump, so it can be restored by hand with no tooling available.

5.1 A rule worth knowing: plan vs actual

The crew roster and expense estimates are a planning layer. Real spend comes from ERPNext purchase invoices. The two are deliberately never reconciled automatically — someone can be on the roster with no bill raised, or billed without ever being on the roster.

Neither figure is ever back-filled from the other. If an expense was logged with no estimate, its "planned" column shows ₹0, not a copy of the actual. The studio's standing rule is that money is never guessed.

6. Life of a request

Following one page load end to end, using the projects list:

1.  Browser requests  https://studioos.example.com/projects
2.  Cloudflare Access checks the session cookie
      └─ not signed in?  email one-time-code challenge, request never reaches the app
3.  Pages serves the React SPA (one JS bundle, one CSS file)
4.  React Router renders <ProjectsListPage>
5.  TanStack Query calls  fetch('/api/projects')
6.  The Worker route /api/projects runs:
      ├─ createFrappeClient(env)          — reads the secrets, never exposed to the browser
      ├─ getList('Project', …)            — 1 ERPNext call
      └─ Promise.all([ tasks, invoices ]) — 2 more calls, batched not per-project
7.  Enrichment in the Worker:
      ├─ checklist progress %             — completed ÷ actionable tasks
      ├─ current phase                    — first incomplete task's phase header
      └─ smartAction                      — the "what's next" button, rule-based
8.  JSON returns; React renders the table
Three calls, not sixty Step 6 fetches all tasks and all invoices for all 32 projects in two batched queries, rather than two queries per project. That mattered on the old Node server; it matters more on Workers, where each outbound call counts against a per-request limit.

6.1 One endpoint that also writes

GET /api/project/:name is not a pure read. On every load it:

  • auto-ticks milestone tasks whose condition is now met (shoot date passed, invoice cleared, crew paid);
  • creates the "Vendor Payment Made" task the first time vendor involvement appears;
  • recalculates whether the project is complete and writes that status back to ERPNext.

This is inherited deliberately from the old app — it is what keeps a project's status honest without anyone remembering to click anything. Because of it, the page is configured not to refetch on window focus, so idly leaving a tab open does not re-run those writes.

8.1 Money rules enforced server-side

Every one of these is enforced in the Worker regardless of what the browser already checked — a client-side check is a convenience, not a control:

  • Invoices are always created as drafts. Nothing reaches the ledger until an explicit, confirmed submit.
  • A submitted invoice is never edited — it is cancelled and re-issued, and a written reason is required, logged on both documents.
  • A payment can never exceed the invoice's outstanding balance.
  • A second draft payment against the same invoice returns 409 rather than silently duplicating.
  • Draft invoices are excluded from "money owed" — a draft was never sent.
  • Cancelled invoices are excluded from every money total — they were reversed in the ledger.

10. How correctness is proven

92 tests, and every one of them has been watched to fail. A test that has never failed proves nothing — it might be asserting something that is true no matter what the code does. So for each area, the logic was deliberately broken, the tests were confirmed red, and the break was reverted.

What was broken on purposeWhat the tests caught
Swapped the pre/production regex order"Pre-Production" classified as production — wrong next-step button on every project still in prep
Dropped + 1 from the invoice sequenceFirst invoice of the year numbered _00_; the second would collide — two clients holding the same invoice number
Removed the cancelled-invoice filterOutstanding shown as ₹1,09,999 instead of ₹10,000
Removed the "has activity" guardEvery untouched project marked Complete — and that status is written back to ERPNext
Changed the payment ceiling to the invoice total₹1,10,000 accepted against a ₹55,000 remaining balance — a double charge
Matched the owner by supplier_name not supplier"Owed to others" jumped ₹3,000 → ₹25,000 — the owner appearing to owe outsiders money owed to himself

Why totals are checked, not just row counts A row count would not catch a value that imported as zero. The verification script compares ₹1,51,741 of transactions, ₹13,550 of rental sessions and ₹14,400 of crew roster totals as well as counting the rows, and exits non-zero on any mismatch so it can gate a deploy.

12. What happens next

  1. Phase 0 — old app safety. A private git remote, atomic ledger writes, and untracking the JSON data files. Small, and it removes the one risk that cannot be undone.
  2. Phase 4 — the last three routes and their pages. The D1 tables already exist, are seeded, and are covered by the backup and verification scripts. Only the routes and pages are missing.
  3. Phase 5 — deploy. Everything is prepared and locally verified; docs/DEPLOY.md has every command in order. One decision is still open: whether to use a custom domain, which determines how the SPA reaches the API.
  4. Phase 6 — cutover. Run both apps side by side, compare page by page, freeze the old app, archive it. Never delete it.

12.1 Known gaps, stated plainly

  • Creating and submitting invoices and payments is unverified end to end. The guard rails are tested and confirmed to reject bad input, but the happy path has not been exercised against the live site, because doing so writes real documents into the studio's accounting. It needs a throwaway customer, set up deliberately.
  • The equipment catalogue page has not been rebuilt. It reads the same ERPNext data as Inventory with a narrower filter, so it may no longer need to exist separately — a product decision, not a technical one.
